# NEXVARY-DA Engineering Stages 181–250

These stages are implementation checkpoints. A stage range is accepted only when the resulting repository tree passes cross-platform CI.

## 181–200 — Guarded plan execution

- Runtime ToolKernel backed by NEXVARY file, Git, shell, build, QA, release and Android adapters.
- Strict plan review against registered tools.
- Unknown actions are rejected.
- Required permissions are derived from the actual runtime declaration.
- Missing permissions reject the plan before execution.
- Read-only versus mutation-capable plans are distinguished.
- Mutation-capable actions require explicit NEXVARY approval.
- Dry-run is the execution default.
- Execution receipts retain before/after commit and changed-file evidence.
- Plan review/execution is exposed through MCP.
- ZCode remains a planning worker and never bypasses this layer.

## 201–220 — Checkpoint, Compact and Resume

- Durable checkpoint store under `.nexvary-da/checkpoints`.
- Atomic checkpoint writes.
- Git branch/commit and changed-file evidence.
- SHA-256 evidence for bounded changed files.
- No source-file contents are copied into checkpoints.
- Sensitive metadata redaction.
- Authorization/token-like text redaction.
- Latest-checkpoint and bounded-history retrieval.
- Deterministic checkpoint retention/pruning.
- Compact resume context combining current state, latest checkpoint and recent events.
- Checkpoint/Resume surfaces available through MCP and CLI.

## 221–235 — Android static quality gate

- AndroidManifest discovery.
- Manifest XML validation.
- MAIN/LAUNCHER detection.
- Missing `android:exported` detection for components with intent filters.
- Cleartext-traffic warning.
- Android resource XML validation.
- `@string/` reference integrity checks.
- Hardcoded UI text warnings.
- Base string inventory.
- Locale completeness comparison.
- Android QA evidence integrated into strict Release Gate when applicable.

## 236–250 — Provenance and project diagnostics

- Deterministic source-file inventory.
- Per-file SHA-256 fingerprints.
- Aggregate source-root SHA-256.
- Generated/internal/build directories excluded from source provenance.
- Artifact manifest linked into provenance.
- Git branch/commit recorded when available.
- Platform/Python environment evidence.
- Provenance verification detects source drift.
- Atomic provenance write.
- Project Doctor checks config, build profile, state database, Git tool, ZCode and Android QA.
- Doctor result is persisted in durable state.
- CLI commands: `doctor`, `checkpoint`, `resume-context`, `provenance`.
- MCP commands: Project Doctor, Android static QA and release provenance.

## Stage 250 completion rule

Stage 250 is a verified engineering baseline, not the end of the product roadmap. Runtime screenshot/interactive UI automation, signed native installers and production cloud-provider credentials remain separate deliverables and must not be reported as complete until independently verified.
