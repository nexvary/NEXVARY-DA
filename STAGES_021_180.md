# NEXVARY-DA Engineering Stages 021–180

Stages are engineering checkpoints, not cosmetic counters. A range is complete only when its implementation is committed and the repository CI accepts the resulting tree.

## 021–040 — Cloud intelligence boundary
- Environment-only credential references; no API keys in project state.
- HTTPS-only provider configuration with bounded timeouts and response sizes.
- Provider-neutral OpenAI-compatible chat-completions adapter.
- Explicit ReasoningRequest payload: no automatic project-file upload.
- Provider errors normalized without leaking credentials.
- Cloud output remains reasoning only; local execution remains authoritative.

## 041–060 — Orchestration and targeted verification
- Strict JSON execution plans; free-form prose cannot execute.
- Tool names are syntax validated and must already be registered in ToolKernel.
- Per-run allowlists and dry-run support.
- Stop-on-error semantics and durable ToolKernel event evidence.
- Dependency DAG with cycle detection, ready-set calculation and failure blocking.
- Change-aware test-selection profiles for Python, Gradle, Node and CMake.

## 061–080 — Static QA and source inspection
- Python AST audit for syntax errors, eval/exec, shell=True and bare exceptions.
- Local Markdown dead-link validation with workspace-bound path resolution.
- HTML route graph and orphan-page detection.
- Tk button command audit.
- JSON localization key completeness across locale files.
- Arabic-script/RTL signal audit.

## 081–100 — Workspace and artifact evidence
- Escaping-symlink detection.
- Case-collision detection for cross-platform safety.
- Oversized source-file detection.
- Release artifact discovery.
- Streaming SHA-256 generation.
- Machine-readable artifact manifest.

## 101–120 — Android execution profile
- Android SDK, Java, ADB and Gradle-wrapper discovery.
- Gradle assembleDebug/test/lint adapters.
- Independent ADB permission requirement.
- Workspace-bound APK installation.
- Android adapter integrated into ProjectRuntime.

## 121–140 — GitHub and release policy
- Canonical GitHub repository validation.
- Permission-gated local GitHub REST client.
- PR, Actions workflow, artifact and release retrieval.
- Draft-release creation requires both Network and Release permissions.
- GitHub tokens are read from environment only.
- Release policy supports auto/required/disabled applicability.
- GitHub client integrated into ProjectRuntime.

## 141–160 — Evidence-producing Release Gate
- Node build/test uses explicit build profile.
- CMake configure/build/test path added.
- Separate integration-suite auto-detection.
- Python static-analysis evidence replaces its previous placeholder.
- Dead-link, orphan-page, button, RTL and localization checks become real when applicable.
- Workspace-health evidence is required.
- UI interaction gate remains fail-closed until runtime screenshot/interaction automation exists.

## 161–180 — Resume, MCP and operational hardening
- State schema v2.
- Recent durable event retrieval with bounded limits.
- Historical gate-run retrieval.
- Event pruning with deterministic retention.
- MCP managed-process start/status/cancel.
- MCP recent-event access.
- MCP Android environment/device access.
- MCP GitHub PR/Actions/Release snapshot.
- Stage ledger and project-state documentation updated.
- Stage 180 candidate must pass Windows and Ubuntu CI before becoming the verified baseline.

## Stage 180 completion rule

Stage 180 does **not** mean every future feature is complete. It means the capabilities listed above are implemented and cross-platform CI-verified. Runtime screenshot automation, interactive desktop/Android UI traversal, signed installers, and a user-selected production cloud provider remain separate future work and must not be reported as complete until independently verified.
